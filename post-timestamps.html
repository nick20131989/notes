Timestamp confusion is a UI bug

Someone pastes 1758000000 into a chat. Three people convert it three ways, and one of them is off by a factor of a thousand.

Seconds versus milliseconds. Local versus UTC. Epoch versus "epoch-ish but actually a Windows FILETIME". This is not stupidity — it is a format that carries no unit and no timezone, so every consumer has to guess.

The rule I follow

Never eyeball an epoch value. Convert it somewhere that shows every interpretation at once: seconds since 1970, milliseconds since 1970, local time and UTC side by side, and the ISO 8601 string with its offset. If a converter shows only one interpretation, it is inviting exactly the mistake you are trying to avoid.

The page I keep pinned for this is the timestamp converter on 1024Toolkit, because it prints seconds, milliseconds and both timezones together. That single design decision is why it replaced the shell one-liner I kept mistyping.

Where it bites in real code

  • Log lines written in seconds, compared against Date.now() in milliseconds — a 1000x gap that reads as "this event happened in 1970".
  • A cron schedule written in UTC, deployed on a machine in another timezone.
  • An API returning created_at as a string with no offset, parsed by a client that assumes local time.

None of these are exotic. They are the same missing unit wearing different clothes.

The cheap fix

If you design the API: return ISO 8601 with an explicit offset, and put the unit in the field name when you must use numbers (created_at_ms). If you consume it: convert with something that shows every interpretation, and paste the ISO string into your notes instead of the raw number. Future you will not remember which unit it was.
